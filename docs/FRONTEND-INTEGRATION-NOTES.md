# Module 1 Frontend — Backend Integration Notes

What the Next.js student frontend (`module1-frontend/`) relies on from the backend,
and where the available contract (`API-SPECIFICATION.md`, `DATABASE-SCHEMA.md`,
`INTEGRATION-GUIDE.md`, `tests/public/`) is silent. Items are things the backend
should confirm or provide; the frontend does not wait on them (it talks to the real
backend by default; set `NEXT_PUBLIC_USE_MOCKS=true`, e.g. in the git-ignored
`.env.local`, for mock mode — the Docker image is built with it off).

Status key: **Required** = the frontend's behaviour depends on it. **Confirm** = the
contract is silent/ambiguous and the frontend made a safe assumption.

## 0. Verified against the real backend (2026-10-22 to 2026-10-24)

Checked by reading `origin/module2-backend` (7963b06) and `origin/module3-face-recognition` (eabf854), and by **running** the backend (SQLite, in-memory Redis stand-in), the face service and the built frontend together, driven through a browser test of 33 steps (login, sessions, every check-in outcome, history, a real rejected check-in followed by an appeal, face enrollment with a real face photo, token refresh). Items marked ✅ in the tables below were exercised in that run; points marked *(code only)* were read in the backend code but not run live, and points marked *(stub-tested)* were checked in a browser against a throwaway test stub that mimics what the backend code does — not against the live backend, unless the text says the point was also re-run live (see the live re-run paragraph below).

**Behaviour confirmed (the frontend relies on it)**

* Login: `401` bad credentials, `403` "Account disabled", `429` "Account locked" (after 10 failed logins; `ACCOUNT_LOCKOUT_ATTEMPTS`). The lock has no timeout: the only code that clears it is the admin `PATCH /admin/users/{id}/activate` (verified in the backend code and confirmed by the backend owner; the lock and the admin unlock were also run live on 2026-10-24: ten wrong passwords gave nine `401`s and then `429` "Account locked", a refresh for the locked account gave `429` "Account locked", and the admin activate endpoint unlocked the accounts; the `403` is still code only). Lockout and rate limiting both return `429` but with different `detail` ("Account locked" vs "Rate limit exceeded"), so a client can tell them apart. Register: `400` "Email already registered".
* Check-in refusals are fixed sentences in `detail`: `400` "Session not active", "Check-in window closed" (before opening **or** after closing), "Student is not enrolled in this course", "Already checked in", "Invalid or missing QR code"; **`403`** "Check-in not allowed from this location"; `404` "Session not found". The frontend maps exactly these to friendly messages (the raw text is never shown). *(Code only: "not enrolled" and the QR refusal were not run live. This project has no QR codes.)*
* A check-in more than twice the geofence radius away is **rejected** (`201`, `status: "rejected"`, factor `geo_out_of_bounds`); a failed liveness check is also rejected.
* `GET /sessions/my-sessions` honours `status` (run live) and `upcoming`/`limit` (code only), and returns `course_code`, `course_name`, `total_enrolled`, `checked_in_count` and `qr_code_enabled`.
* Appeals (`POST /checkins/{id}/appeal`, body `{appeal_reason}`): only for flagged or rejected check-ins, once, within 7 days of the check-in (backend-enforced: `400` "Appeal window has closed"); `appeal_reason` has no maximum length in the backend schema (the frontend caps it at 1000 characters on its own); appealed check-ins are included in the instructors' flagged queue (all verified in the backend code and confirmed by the backend owner). The status becomes `appealed`.
* Face enrollment (`POST /users/me/face/enroll`): `200` `{success, message, face_enrolled, quality_score}` (`quality_score` can be null); `400` "Camera consent not given" or "No face detected"; `503` when the face service is down. Re-enrolling simply replaces the template.

**Things the frontend works around (better fixed at the source)**

1. **Timestamps have no time-zone marker** (e.g. `2026-10-22T10:28:29.910000`) although they are UTC. Browsers read such strings as local time (8 hours off in Singapore), so the frontend treats marker-less timestamps as UTC (`lib/dates.ts`). Sending a trailing `Z` would remove the ambiguity.
2. `my-sessions?status=active` still lists a session whose **check-in window has already closed**; the frontend only warns on the preflight screen (from the dates), and the backend then refuses with "Check-in window closed".
3. Check-in is allowed **only from Singapore** (coordinates inside a Singapore bounding box, and a private or Singapore IP). Anyone outside, or behind a foreign VPN, gets the `403` above.
4. CORS defaults to `http://localhost:3000,http://localhost:8501`; any other frontend origin (a phone tunnel, another port) must be added through `CORS_ORIGINS`.

**For the backend / face-module owners (not frontend bugs)**

* **Without Redis the in-memory rate-limit fallback is racy**: concurrent first requests can fail with a `redis` `TimeoutError` and answer `500` **without CORS headers**, which the browser reports as a network failure. (Suspected cause, from reading the code and not isolated: `get_redis()` publishes the client before `ping()` has succeeded.) Not an issue with Redis running.
* **Face matching does not protect anything yet.** In the default profile an identical image matches (`face_match_passed: true`), but a different photo, even of the same person, fails (`face_match_failed`), and **a failed match still ends `approved`** (risk 0.28 is below the 0.5 threshold). A different person's photo behaves the same way. (Seen again live on 2026-10-24: both mismatching check-ins were approved with a `face_match_failed` factor.)
* Passive liveness rejects a **still photo filmed by a camera**, so demos need a live face.
* The backend maps every face-service 4xx (including "image too large") to "No face detected".

**Not verified here:** PostgreSQL (SQLite was used), Docker Compose (no engine was available, so the frontend Dockerfile was not built; equivalent plain Next.js builds were run), a real phone over HTTPS. QR codes are not part of this project (confirmed by the team).

**Public test suite (native, SQLite + fake Redis, 2026-10-23):** `pytest tests/public/` gave **88.0/92.0**: 91 passed, 5 failed, 1 skipped. The three failing bonus tests (`stats/courses`, `stats/students`, `enrollments/course`) get `403` for the test instructor; two zero-point tests call `GET /courses/` without a token and get `401`. The skip is a hard-coded `@pytest.mark.skip` (`test_performance.py:93`).

**Live re-run of the latest frontend commit (`acd3cdb`, 2026-10-24; real backend on SQLite with the in-memory Redis stand-in, built frontend, fake data only).** The 33-step browser suite passed **33/33** (face service stopped, synthetic camera, spoofed Singapore GPS, as in the first run), and 15 further live checks passed with the real face service running:

A different photo of the same person, and a different person, were both **approved by the backend with a `face_match_failed` factor**, and the History detail showed the amber "Checked in, but your face wasn't confirmed" warning with the "Face match: Did not match" row; the list badge stayed "Approved" (the server status is unchanged).

### Duplicate submissions — what the frontend does and what was verified

Frontend guard: a ref-based in-flight lock plus a disabled button means one user action
produces at most one submission call (`CheckInFlow.handleSubmit`). Any failure is surfaced
for the student to retry explicitly.

Why the backend still must be idempotent, demonstrated in Chromium (the in-app browser,
same-origin `fetch` and `XMLHttpRequest`, against a throwaway Node server on localhost
that reads the full POST then destroys the socket, counting what it received):

* A **single** `fetch(POST)` / `XHR POST` call, sent on a **reused keep-alive connection**
  that the server then reset, arrived at the server **twice** (the second on a fresh
  connection), although the page code called it once. The page saw one failure.
* The same POST on a **fresh connection** (no pooled socket) arrived **once**.

So the browser's network stack can replay a POST when a pooled connection dies, and the
first copy may already have been processed. That is a lost-response scenario the frontend
cannot prevent, which is why duplicate protection belongs on the backend (item 1.1). This
was observed on one browser engine only; do not read it as a guarantee about every browser.

## 5. PWA / offline behaviour (what the frontend does)

* **Installable**: `public/manifest.json` + placeholder icons (`public/icons/`, replace with real branding), `public/sw.js`. The service worker is registered in **production builds only**; in `next dev` it is never registered and any stray SAIV worker on that origin is removed.
* **Offline**: the app shell (`/`) and its hashed JS/CSS load with no connection. Everything that talks to the backend still needs one: sign-in, loading sessions, checking in. An offline banner explains this and the Start/Submit buttons are disabled while the browser reports offline.
* **What the worker caches**: only the shell page, `/_next/static/*`, the manifest and icons. **It never handles** non-GET requests (so check-in POSTs are never cached or replayed by it), cross-origin requests (the API), requests with an `Authorization` header, `/api/` paths, RSC/prefetch requests or range requests. No tokens, API responses or check-in data are cached.
* **Install requires everything the shell needs to render**: every `<script>` / stylesheet the shell page loads must be fetched and cacheable, otherwise installation fails (the worker never activates, the app keeps working online). These fetches are all checked before the first cache write, so a failed fetch writes nothing. The cache writes themselves are not transactional: if a write fails (e.g. storage quota), install still fails but entries already written may remain; they are valid files from the same build, are not served without an active worker, and are overwritten by the next install. The manifest, icons and other chunk names are optional — a failure is logged with `console.warn` and skipped.
* **Not done on purpose**: no background sync and **no deferred check-in queue** — nothing is ever sent later on the student's behalf.
* **HTTPS**: service workers, camera, geolocation and Web Crypto need a secure context (HTTPS or `localhost`). Installing on a phone needs the app served over HTTPS.
* **Deploy note**: `/_next/static/*` files are content-hashed, so they never go stale. The **manifest and icons are not hashed and are cached once at install without revalidation**, so after changing them (e.g. replacing the placeholder icons), bump `CACHE_VERSION` in `public/sw.js` or installed clients keep the old ones. Bump it too whenever the worker's own caching rules change.
